نعم، ممكن جدًا عمل تطبيق ترفع فيه بوست أو فيديو مرة واحدة ثم ينشر على عدة منصات، لكن ليس كل المنصات بنفس السهولة أو بنفس صلاحيات النشر المباشر. بعض المنصات تدعم النشر عبر APIs الرسمية مثل Instagram/Facebook عبر Meta Graph API، وYouTube عبر YouTube Data API، وTikTok عبر Content Posting API، لكن كل منصة لها شروطها وحدودها الخاصة.

كيف يكون الفكرة
التطبيق يكون فيه:

كتابة الكابشن.

اختيار المنصات المطلوبة.

تعديل بسيط لكل منصة إذا لزم، مثل طول النص أو الهاشتاقات.

جدولة النشر أو النشر الفوري.
أدوات الجدولة المعروفة أصلًا تعمل بهذه الطريقة، حيث تسمح بكتابة المحتوى مرة ثم تخصيصه لكل قناة قبل النشر.

أهم القيود
Instagram وFacebook يحتاجان حسابات مناسبة وصلاحيات وربط بحساب Business/Creator في كثير من الحالات.

YouTube يسمح برفع الفيديوهات عبر API لكن يستهلك من quota يومية، ورفع الفيديو الواحد يكلف 1600 وحدة تقريبًا، لذلك يوجد حد عملي بعدد الرفعات يوميًا.

TikTok يدعم النشر عبر API، لكن عادة يتطلب مراجعة للتطبيق وصلاحيات محددة، وبعض التدفقات تكون أكثر تعقيدًا من غيرها.

بعض المنصات لا تسمح بنفس شكل النشر لكل أنواع المحتوى، لذلك أحيانًا تحتاج نسخة مختلفة للفيديو أو الوصف حسب المنصة.

أفضل تصميم عملي
الأفضل ليس “زر واحد ينشر كل شيء بدون تفكير”، بل نظام ذكي يعمل هكذا:

يجهز نسخة أصلية من المحتوى.

يحولها تلقائيًا لصيغ مناسبة لكل منصة.

يضيف كابشن مختلف إذا احتاج.

يتأكد من المقاسات والمدة.

ثم ينشر أو يرسل للمراجعة قبل النشر.
هذا يقلل الأخطاء ويجعل التطبيق أقرب للاستخدام الاحترافي بدل النشر العشوائي.

هل هذا مناسب لك؟
نعم، ومناسب جدًا خصوصًا لو هدفك إدارة محتوى لنشاط أو أكاديمية، لأنك تقدر توحّد النشر من مكان واحد وتوفر وقت كبير. والأفضل يبدأ التطبيق أولًا بمنصات محددة مثل Instagram + Facebook + YouTube Shorts، ثم تضيف TikTok بعد ذلك حسب الصلاحيات والتكامل.

أقدر أيضًا أوضح لك تصميم التطبيق المناسب أو أرسم لك خطة تقنية كاملة: واجهات، قاعدة بيانات، وAPIs المطلوبة.

2) SQL الجاهز
sql
-- 1. Users
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  full_name VARCHAR(200) NOT NULL,
  email VARCHAR(255) NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  role VARCHAR(50) NOT NULL DEFAULT 'admin',
  is_active BOOLEAN NOT NULL DEFAULT TRUE,
  last_login_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 2. Social accounts
CREATE TABLE social_accounts (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  platform VARCHAR(50) NOT NULL, -- instagram, facebook, youtube, tiktok
  platform_account_id VARCHAR(255),
  account_name VARCHAR(255),
  access_token TEXT,
  refresh_token TEXT,
  token_expires_at TIMESTAMPTZ,
  permissions JSONB,
  status VARCHAR(50) NOT NULL DEFAULT 'connected', -- connected, expired, revoked, error
  metadata JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (user_id, platform, platform_account_id)
);

CREATE INDEX idx_social_accounts_user_id ON social_accounts(user_id);
CREATE INDEX idx_social_accounts_platform ON social_accounts(platform);

-- 3. Posts
CREATE TABLE posts (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title VARCHAR(255),
  caption TEXT NOT NULL,
  status VARCHAR(50) NOT NULL DEFAULT 'draft', -- draft, scheduled, publishing, published, failed, archived
  post_type VARCHAR(50) NOT NULL DEFAULT 'video', -- video, image, reel, shorts, story
  is_template BOOLEAN NOT NULL DEFAULT FALSE,
  language VARCHAR(20) DEFAULT 'ar',
  metadata JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  published_at TIMESTAMPTZ
);

CREATE INDEX idx_posts_user_id ON posts(user_id);
CREATE INDEX idx_posts_status ON posts(status);
CREATE INDEX idx_posts_created_at ON posts(created_at DESC);

-- 4. Post assets
CREATE TABLE post_assets (
  id BIGSERIAL PRIMARY KEY,
  post_id BIGINT NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  asset_type VARCHAR(50) NOT NULL, -- image, video, thumbnail
  storage_provider VARCHAR(50) NOT NULL DEFAULT 'cloudinary', -- cloudinary, s3, local
  file_url TEXT NOT NULL,
  file_path TEXT,
  mime_type VARCHAR(100),
  file_size_bytes BIGINT,
  width INT,
  height INT,
  duration_seconds NUMERIC(10,2),
  checksum VARCHAR(128),
  sort_order INT NOT NULL DEFAULT 1,
  metadata JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_post_assets_post_id ON post_assets(post_id);

-- 5. Platforms target per post
CREATE TABLE post_targets (
  id BIGSERIAL PRIMARY KEY,
  post_id BIGINT NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  platform VARCHAR(50) NOT NULL, -- instagram, facebook, youtube, tiktok
  social_account_id BIGINT REFERENCES social_accounts(id) ON DELETE SET NULL,
  target_status VARCHAR(50) NOT NULL DEFAULT 'pending', -- pending, queued, publishing, published, failed, skipped
  external_post_id VARCHAR(255),
  external_url TEXT,
  caption_override TEXT,
  hashtags TEXT[],
  scheduled_for TIMESTAMPTZ,
  published_at TIMESTAMPTZ,
  error_code VARCHAR(100),
  error_message TEXT,
  metadata JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (post_id, platform, social_account_id)
);

CREATE INDEX idx_post_targets_post_id ON post_targets(post_id);
CREATE INDEX idx_post_targets_status ON post_targets(target_status);
CREATE INDEX idx_post_targets_scheduled_for ON post_targets(scheduled_for);

-- 6. Publish jobs
CREATE TABLE publish_jobs (
  id BIGSERIAL PRIMARY KEY,
  post_target_id BIGINT NOT NULL REFERENCES post_targets(id) ON DELETE CASCADE,
  job_type VARCHAR(50) NOT NULL DEFAULT 'publish', -- publish, retry, delete, update
  queue_name VARCHAR(100) NOT NULL DEFAULT 'publish-queue',
  status VARCHAR(50) NOT NULL DEFAULT 'queued', -- queued, running, completed, failed, cancelled
  attempts INT NOT NULL DEFAULT 0,
  max_attempts INT NOT NULL DEFAULT 3,
  priority INT NOT NULL DEFAULT 5,
  run_after TIMESTAMPTZ,
  started_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,
  locked_by VARCHAR(255),
  locked_at TIMESTAMPTZ,
  input_data JSONB,
  output_data JSONB,
  error_message TEXT,
  error_stack TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_publish_jobs_status ON publish_jobs(status);
CREATE INDEX idx_publish_jobs_run_after ON publish_jobs(run_after);
CREATE INDEX idx_publish_jobs_post_target_id ON publish_jobs(post_target_id);

-- 7. Publish logs
CREATE TABLE publish_logs (
  id BIGSERIAL PRIMARY KEY,
  publish_job_id BIGINT REFERENCES publish_jobs(id) ON DELETE CASCADE,
  post_target_id BIGINT NOT NULL REFERENCES post_targets(id) ON DELETE CASCADE,
  log_level VARCHAR(20) NOT NULL DEFAULT 'info', -- info, warning, error, debug
  event_name VARCHAR(100) NOT NULL, -- queued, started, api_request, api_response, success, failed, retry
  message TEXT NOT NULL,
  request_payload JSONB,
  response_payload JSONB,
  http_status INT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_publish_logs_publish_job_id ON publish_logs(publish_job_id);

3) العلاقات بين الجداول
المستخدم الواحد يمكن أن يملك عدة حسابات اجتماعية.

كل post يمكن أن يحتوي عدة ملفات وسائط.

كل post يمكن أن يُرسل إلى عدة منصات عبر post_targets.

كل post_target يمكن أن يمر بعدة publish_jobs عند إعادة المحاولة.

كل publish_job يكتب سجلاته في publish_logs.
هذا مهم لأن المنصات قد تنجح أو تفشل بشكل مستقل، وتحتاج تتبع منفصل لكل هدف نشر.

4) حالات العمل المقترحة
أنصح توحيد الحالات التالية:

posts.status: draft, scheduled, publishing, published, failed, archived

post_targets.target_status: pending, queued, publishing, published, failed, skipped

publish_jobs.status: queued, running, completed, failed, cancelled
وجود هذه الحالات يجعل لوحة التحكم واضحة ويمنع التباس المنشور الأساسي مع نتيجة كل منصة.

5) ملاحظات تنفيذ مهمة
اجعل كل ملف فيديو أو صورة يُرفع أولًا إلى S3 أو Cloudinary ثم خزّن الرابط في post_assets.

استخدم publish_jobs مع Redis/BullMQ للمهام الخلفية، لأن النشر يحتاج retries وtimeouts ومراقبة حالة التنفيذ.

خزّن request_payload وresponse_payload في publish_logs لتسهيل الدعم الفني لاحقًا.

اجعل scheduled_for في post_targets هو المرجع الفعلي للنشر إن كانت لكل منصة وقت مختلف.

لو عندك إعادة نشر تلقائية، استخدم recurrence_rule داخل schedules بصيغة نصية أو iCal RRULE.

6) بداية التنفيذ
أفضل ترتيب للتطبيق:

أنشئ الجداول السابقة.

اربط صفحة إنشاء المنشور بجدول posts.

ارفع الوسائط إلى post_assets.

أنشئ post_targets عند اختيار المنصات.

عند الجدولة، أنشئ publish_jobs.

worker ينفذ النشر ويحدّث publish_logs وpost_targets.
هذا الترتيب يحول النظام من فكرة نظرية إلى نظام قابل للتشغيل والمراقبة من أول نسخة.
